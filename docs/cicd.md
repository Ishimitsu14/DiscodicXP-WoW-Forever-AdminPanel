# CI/CD сервера

Workflow `.github/workflows/server.yml` запускает проверки для pull request в `main`.
Push в `main` после успешных проверок автоматически обновляет сервер. Можно повторить
деплой через **Actions → Server → Run workflow**, выбрав `main`.

CI передаёт архив точного коммита, а не выполняет `git pull` на сервере. Зависимости
устанавливаются в соседнем каталоге до остановки службы. Затем заменяется каталог
приложения, запускается `discodicxp-update` и проверяются внутренний и публичный
`/health` с обычной проверкой HTTPS-сертификата. При ошибке возвращается предыдущий
код и перезапускается служба. `/etc/discodicxp`, `/var/lib/discodicxp` и
`/srv/discodicxp-downloads` не заменяются. Откат кода не откатывает схему и данные БД;
изменения схемы должны сохранять совместимость с предыдущим кодом.

На сервере остаются предыдущий каталог `<install>.next.<id>.previous` и, при ошибке,
новый каталог `<install>.next.<id>.failed`. Развёрнутый SHA записан в
`/opt/discodicxp-update/.deploy-revision` и в итогах GitHub Actions.
SSH-команды и смену файлов выполняет workflow; вручную повторять их после push не нужно.

## Однократная настройка

Служба, Node.js, HTTPS и постоянные каталоги уже должны существовать. Первичная
установка описана в README; CI не переустанавливает nginx, сертификаты или systemd unit.

Создайте отдельный SSH-ключ для GitHub Actions без passphrase. Его **публичную** часть
добавьте в `~/.ssh/authorized_keys` пользователя сервера. Пользователь должен быть
`root` либо иметь разрешённый `sudo -n` для команд развёртывания. Приватный ключ
не добавляется в Git, Deploy keys репозитория или чат.

В **Settings → Secrets and variables → Actions** этого репозитория добавьте:

| Repository secret | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP или домен сервера, без `https://`; текущая установка — `153.76.170.60` |
| `DEPLOY_USER` | Пользователь SSH |
| `DEPLOY_SSH_KEY` | Полный приватный ключ, включая строки BEGIN/END |
| `DEPLOY_KNOWN_HOSTS` | Проверенная запись сервера в формате OpenSSH `known_hosts` |

Для `DEPLOY_KNOWN_HOSTS` используйте запись уже доверенного SSH-подключения либо
сверьте fingerprint с `/etc/ssh/ssh_host_ed25519_key.pub` через консоль провайдера.
Для нестандартного порта запись имеет вид `[host]:port ssh-ed25519 ...`.
Workflow проверяет host key строго и не получает его вслепую через `ssh-keyscan`.

Необязательные **Variables**:

| Variable | По умолчанию |
| --- | --- |
| `DEPLOY_PORT` | `22` |
| `DEPLOY_ORIGIN` | `https://<DEPLOY_HOST>`; укажите настоящий публичный origin, если SSH-домен отличается |

Job использует environment `production`; секреты можно вместо repository secrets
разместить в этом environment. Для полностью автоматического деплоя не включайте
обязательное ручное подтверждение environment.

Те же SSH-настройки добавьте в клиентский `DiscodicXP-WoW-Forever`: его workflow
после GitHub Release лаунчера обновляет только EXE, checksum и манифест. SSH-ключ
нужен для направления **GitHub Actions → сервер**. Ключ сервера в GitHub Deploy keys
нужен для обратного направления и в этой схеме не используется.

## Первый запуск

1. Добавьте секреты и публичный SSH-ключ.
2. Отправьте workflow и сопутствующие файлы в `main` этого репозитория.
3. Дождитесь зелёных `check` и `deploy` в Actions. При ошибке исправьте настройку
   или код и повторите workflow, не обходя его ручным деплоем.
4. После первого успешного запуска можно публиковать релиз лаунчера по инструкции
   `docs/cicd.md` клиентского репозитория.

Root-тесты деплоя и publisher выполняются в CI отдельно через `sudo`, поэтому
Linux-проверки не остаются пропущенными из-за непривилегированного runner.
