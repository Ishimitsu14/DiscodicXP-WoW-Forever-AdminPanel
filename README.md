# DiscodicXP · Admin

Админка, API прогресса и сервер обновлений Windows-лаунчера DiscodicXP.
Клиентская часть — аддон и лаунчер — хранится отдельно:
[DiscodicXP-WoW-Forever](https://github.com/Ishimitsu14/DiscodicXP-WoW-Forever).

Node.js 22.14+, SQLite, обычные ES modules. Веб-интерфейс на HTML/CSS/JavaScript
без отдельной сборки. SQLite доступен через встроенный `node:sqlite`; в Node 22
он выводит предупреждение об экспериментальном API. Данные находятся в `data/`
и в Git не включаются.

## Возможности

- Аккаунты с BattleTag, персонажи с GUID, именем и игровым сервером.
- Отдельный ключ для каждого компьютера; в базе сохраняется только его SHA-256.
- Синхронизация полного файла **персонажа** `DiscodicXP.lua`: маршрут, шаги,
  отметки пунктов, путевые точки, история маршрутов, персональные настройки и tracking.
- Проверка Lua как данных; функции, вызовы, присваивание чужих глобальных переменных
  и выражения не принимаются. Lua не исполняется.
- Ревизии и атомарное сохранение в SQLite. Устаревшая запись получает HTTP 409.
- Хранятся последние 20 версий каждого персонажа; история доступна в панели.
- Журнал входов, выдачи/отзыва ключей, отправки и загрузки прогресса.
- Совместимый API приватных обновлений `/v1/releases/latest` и `/v1/packages/:sha256.zip`.

BattleTag в карточке задаёт администратор. Аддон дополнительно сообщает наблюдаемый
BattleTag, если API клиента доступен; это поле `observedBattleTag` не подтверждает
владение Battle.net и не используется для авторизации. Доступ к данным определяется
ключом компьютера и его `accountId`. Регистрация через Battle.net OAuth в v1 не входит.

## Локальный запуск

```powershell
npm.cmd ci --ignore-scripts
```

Создайте **вне репозитория** временный JSON-файл с полями `login` и `password`.
Задайте свой пароль длиной от 12 символов. Не передавайте его через чат,
аргументы процесса или Git. Затем:

```powershell
npm.cmd run setup -- 'C:\absolute\private\admin-credentials.json'
# Удалите этот временный файл после успешного создания администратора.
npm.cmd start
```

Откройте [локальную панель](http://127.0.0.1:8787), войдите, создайте аккаунт
с BattleTag и выдайте ему ключи для первого и второго компьютера. Ключ показывается
один раз. Браузер использует HttpOnly-сессию и CSRF-токен; сеанс действует 8 часов
и завершается при перезапуске сервера. Пароли хранятся в виде scrypt-хешей.

Параметры передаются через окружение; `.env.example` — справочник.
Для `.env` используйте `node --env-file=.env server/index.mjs`.
`PUBLIC_ORIGIN` должен **точно** совпадать с адресом панели. HTTP разрешён только
на loopback; клиентский лаунчер принимает только HTTPS.

## CI/CD

Push в `main` запускает тесты и автоматическое обновление API и админки через
GitHub Actions. Лаунчер доставляется отдельным workflow клиентского репозитория
после GitHub Release. Настройка SSH-секретов и первый запуск: [docs/cicd.md](docs/cicd.md).
После правок вручную подключаться к серверу и выполнять `git pull` не требуется.

## Первичная установка сервера

Нужны Debian/Ubuntu с systemd, публичный IPv4 или домен и открытые 80/443. Изучите скрипт перед запуском.
Передайте содержимое этого репозитория без `data`, `.env` и `node_modules` на сервер:

```bash
sudo bash server/deploy.sh updates.example.com
```

Если сервер уже использует nginx (например, образ с ISPmanager), выберите
отдельный режим без установки Caddy и без изменения сайтов панели:

```bash
sudo bash server/deploy.sh ishimitsu.kk.fvds.ru nginx
```

В этом режиме создаётся только `/etc/nginx/conf.d/discodicxp.conf`, выпускается
сертификат Let's Encrypt через Certbot и включается автоматическое продление.
Конфигурация проверяется перед reload; при ошибке настройки возвращается прежний
конфиг DiscodicXP. Другие конфиги nginx не перезаписываются.

Можно работать по IP без домена:

```bash
sudo bash server/deploy.sh 153.76.170.60 nginx
```

`nginx-ip-proxy.sh` устанавливает Certbot 5.4+ в отдельный Python venv, получает
доверенный IP-сертификат Let's Encrypt с профилем `shortlived` и настраивает
`discodicxp-certbot.timer`. Сертификат действует около шести дней, поэтому проверка
продления выполняется дважды в сутки. ACME-конфигурация изолирована в
`/etc/discodicxp/acme` и не затрагивает сертификаты панели провайдера.

Боевой адрес этой установки: [https://153.76.170.60](https://153.76.170.60).
Этот же адрес нужно указать в Windows-лаунчере.

Скрипт устанавливает Node 22, зависимости и выбранный HTTPS-прокси, создаёт пользователя
`discodicxp-update`, службу с тем же именем, HTTPS-прокси и постоянную базу
`/var/lib/discodicxp/discodicxp.sqlite`. При обновлении старой установки сохраняет
GitHub-токен, реестр прежних ключей и кэш. Старые ключи дают доступ только к
обновлениям; для прогресса выдайте новые ключи в админке.

Проще создать администратора интерактивно без временного файла и без пароля
в аргументах процесса. В собственной SSH-сессии выполните:

```bash
sudo bash /opt/discodicxp-update/server/create-admin.sh
```

Введите логин и новый пароль дважды. Ввод пароля скрыт; в базе остаётся scrypt-хеш.
Либо используйте локальный файл учётных данных:

```bash
sudo -u discodicxp-update env DATABASE_PATH=/var/lib/discodicxp/discodicxp.sqlite \
  /opt/discodicxp-node/current/bin/node /opt/discodicxp-update/server/setup.mjs \
  /absolute/private/admin-credentials.json
```

Файл должен быть доступен служебному пользователю. После выполнения удалите его.
Откройте `https://updates.example.com` и создайте аккаунты/ключи.
Смена домена требует нового `PUBLIC_ORIGIN` в `/etc/discodicxp/service.env` и перезапуска.

Для приватных релизов задайте fine-grained GitHub PAT с `Contents: read`
только для клиентского репозитория. В собственной SSH-сессии:

```bash
read -rs -p 'GitHub token: ' github_secret; printf '\n'
printf '%s' "$github_secret" | sudo /opt/discodicxp-node/current/bin/node /opt/discodicxp-update/server/set-github-token.mjs
unset github_secret
sudo systemctl restart discodicxp-update
```

Прогресс и панель работают без GitHub-токена; получение приватных обновлений — после его настройки.
Рекомендуется резервировать `/var/lib/discodicxp` и `/etc/discodicxp` при остановленной
службе. Для онлайн-копирования SQLite используйте SQLite backup API, а не копирование
одного `.sqlite` без WAL. Нельзя запускать несколько независимых копий службы над одной базой.

## Скачивание лаунчера

Публичная ссылка без входа в админку:
[скачать актуальный лаунчер Windows](https://153.76.170.60/downloads/DiscodicXP.Launcher.exe).
Она также доступна на странице входа и в боковом меню панели.
SHA-256 опубликован [отдельным файлом](https://153.76.170.60/downloads/DiscodicXP.Launcher.exe.sha256).
Ключ компьютера требуется для работы лаунчера с данными аккаунта.

Сборку и доставку лаунчера выполняет GitHub Actions клиентского репозитория
после публикации релиза `launcher-v<версия>`. Workflow сам вызывает
`server/publish-launcher.sh`; вручную загружать EXE не нужно.

Публикация проверяет SHA-256, размер и заголовок exe, затем атомарно заменяет файл.
Скачивание обслуживает nginx из `/srv/discodicxp-downloads`; приложение Node.js
и сессии админки не участвуют в выдаче бинарного файла.

Лаунчер 0.3.0+ проверяет `/downloads/launcher/latest.json` при запуске и предлагает
скачать новую версию внутри приложения. Публикация сначала сохраняет exe по
неизменяемому адресу `/downloads/launcher/<sha256>.exe`, затем заменяет JSON.
Старые бинарные файлы остаются доступны для уже начатых обновлений. В JSON
передаются `version`, `sha256`, `size` и `downloadPath`; ключ компьютера не нужен.
Адрес обновлений самого лаунчера закреплён в клиенте и не зависит от поля сервера аккаунта.

## Протокол прогресса v1

Все запросы лаунчера содержат `Authorization: Bearer dxp_…`.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/v1/account` | Аккаунт текущего ключа |
| GET | `/api/v1/characters` | Только персонажи этого аккаунта |
| POST | `/api/v1/snapshots` | Сохранение с `schemaVersion: 1`, `character: {guid,name,realm}`, `content`, `baseRevision` |
| GET | `/api/v1/characters/:id/snapshot` | Актуальная ревизия и полный файл персонажа |

Начальная `baseRevision` — 0; каждый успешный POST увеличивает ревизию на 1.
Если база отличается от актуальной, сервер возвращает 409 без изменения данных.
Один файл — до 2 МиБ, до 200 персонажей на аккаунт. Лимит истории — 20 снимков.
GUID уникален внутри аккаунта. Все SQL-запросы параметризованы.

Новый компьютер должен хотя бы один раз войти нужным персонажем с аддоном 0.4.0+
и нормально выйти из игры. После этого лаунчер увидит его файл и сможет восстановить
серверный прогресс. Общие файлы аккаунта, импортированные тексты гайдов и другие
аддоны не переносятся; на компьютерах нужен один комплект маршрутов.
При включённом автосохранении открытый лаунчер отправляет прогресс выбранного
персонажа после закрытия WoW. Загрузка на другой компьютер выполняется с подтверждением.

## Публикация гайдов

В разделе «Гайды» нажмите «Загрузить гайд», выберите исходный `.txt` до 16 МиБ
и нажмите «Загрузить и опубликовать». Принимаются зашифрованный контейнер
Forever и открытый текст одного маршрута с `#forever`, `#group`, `#name`, `step`.
Для контейнера нужно сохранить исходное имя файла, включая часть после `!`.
Оно используется при проверке; в истории показывается имя без идентификатора владельца.

Каждая публикация заменяет комплект для всех подключённых компьютеров.
В SQLite сохраняются последние 20 версий; повторная загрузка текущего содержимого
не создаёт новую ревизию. Ошибка проверки сохраняет предыдущую публикацию.
История публикаций доступна в разделе «Гайды» и в журнале.

Игроку нужны лаунчер 0.4.0+ и аддон 0.5.0+. Один раз обновите аддон при закрытой
игре и перезапустите WoW; затем можно нажимать «Обновить гайды» в лаунчере
во время игры и применять результат через `/reload`.

`GET /api/v1/guides/latest` возвращает `schemaVersion`, `revision`, `name`,
`sha256`, `size`, `sectionCount`, `createdAt`, `downloadPath`.
`GET /api/v1/guides/packages/:sha256` отдаёт JSON с `schemaVersion: 1`
и массивом строк `guides`. Оба запроса требуют активный ключ компьютера.
`POST /api/admin/guides` принимает `{fileName, content}` с сессией, Origin и CSRF.
Старые ключи из реестра без аккаунта для гайдов не подходят.

При обновлении существующего nginx увеличьте `client_max_body_size` с `4m`
до `32m` в конфигурации DiscodicXP и проверьте конфигурацию перед reload.
Новые установки используют этот лимит из скриптов развёртывания.

## Проверки

```powershell
npm.cmd test
```

Проверяются два компьютера одного аккаунта, изоляция другого аккаунта, конфликты
параллельных записей, 20 версий истории, отзыв ключа, сессии/CSRF, валидация Lua и
существующий протокол приватных обновлений. Проверки не подключаются к Battle.net.
